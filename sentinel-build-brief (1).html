How to run this brief

The deliverable is a three minute video and a live demo, not a working product. Every decision resolves in favour of the thing that looks right on camera and repeats identically on the tenth run. Hardcoding is not a compromise here, it is the design. A scripted path that plays perfectly beats a real pipeline that stutters. Where something is staged, label it in the README and move on.
  1. Read this whole file first. The event contract in section 04 is what lets six lanes work at once without blocking each other. Freeze it before anyone writes a line.
  2. Create the repo skeleton and the event contract in the first fifteen minutes. Every lane codes against that contract, not against another lane's output.
  3. Spawn one subagent per lane in section 09. Lanes 2, 4, 5 and 6 have no dependencies at all and start immediately against mock events.
  4. Never halt on a failure. Section 10 gives a fallback ladder for every component. Walk down it, write what you landed on into context.md, keep going. A component that will not load is a two line note in the README, never a stalled build.
  5. Timebox every model experiment to the cap written on it. When the cap expires, take the fallback. The night is lost to quantizations that will not load, not to missing features.
  6. Keep the demo path alive at all times. If a branch breaks the end to end run, revert it first and debug after. The run is the product.
  7. Log every measured number (VRAM, latency, tokens per second) into context.md as you get it. Those numbers are the evidence slide and the judges ask for them.
  8. Record a backup take the moment the first clean run happens. Do not wait for polish. A rough recording in hand beats a beautiful one you never got.
01

What the system is

A campus has hundreds of cameras and nobody watching them. Sentinel watches all of them on one machine that never leaves the building, and when something real happens it reaches a dispatcher by itself.

  1. Twelve camera feeds arrive. Six are on screen, all twelve are on the campus map.
  2. A cheap always on router looks at every frame and answers one question: is anything happening here. It is tuned for recall, because a false alarm costs one VLM call and a miss costs everything.
  3. When the router says maybe, a vision language model reads the last few seconds of that camera and decides what it actually saw, with a confidence score taken from token logprobs rather than from anything the model wrote about itself.
  4. Above a threshold the act tier runs, and it is deterministic code, not a model. It pulls the camera's street address, entrance and cross street from the camera map, assembles a Call Brief, and places the call.
  5. The call is answered by a mock dispatch console. A local language model speaks as the caller and may only answer from the Call Brief. A dispatcher asks questions and gets live answers.
  6. Before anything is said or sent, IBM Granite Guardian checks the proposed action and the proposed sentence against the evidence, and blocks what is not grounded. The block is visible on screen.
  7. Every decision lands in an append only governance panel: what the model saw, what it concluded, how confident it was, what Guardian said, and why.
  8. Nothing leaves the machine except the alert. Video never goes to a cloud, which is the entire point of running it locally.
Hero scenario: a medical collapse in a stairwell, seen by three cameras at once. It proves the camera map, cross camera correlation, and the dispatch path in one shot. Build this one first and build it perfectly.

05

The five IBM layers

Each layer is load bearing, not decoration. A judge should be able to remove any one of them and see the demo get worse.

1. Granite Guardian, the gate hero

must work

Two modes, both before the action, never after.

  • Agentic function call check. The act tier proposes dispatch_911(brief). Guardian sees the proposed call plus the evidence and answers whether the call is supported. Only then does it run.
  • Groundedness check on every sentence the caller model is about to speak, against the Call Brief. Ungrounded sentences are blocked and the block is shown.
POST /v1/chat/completions
{ "model": "ibm-granite/granite-guardian-3.2-3b-a800m",
  "messages": [ ...conversation..., {"role":"user","content": guardian_block} ] }

// guardian_block = mode (no-think) + criteria (groundedness | function_call) + scoring schema
// parse the <score> tag: "yes" means risk detected, "no" means clean
// invert carefully. a "yes" on groundedness means the claim is NOT grounded
Build the failure firstDeliberately plant one ungrounded claim that Guardian blocks every single run, identically. A demo where Guardian only ever passes proves nothing. That one blocking shot is the whole IBM story.

2. BeeAI Framework, the call time agent

2 hour cap
  • Python. Linux Foundation project, so it is defensible as open governance rather than vendor lock in.
  • Tools: lookup_location, get_suspect_status, get_elapsed_time, get_person_description, repeat_last.
  • Use BeeAI's built in constraints so deterministic rules govern the agent rather than merely suggesting behaviour. That is the reason we are using it, and it is the sentence to say out loud.
  • Turn on native OpenTelemetry tracing and point it at the audit log.
  • Emit every tool call to the event stream so the dashboard shows the agent working live.
TimeboxTwo hours. If BeeAI resists, keep a plain tool loop with the same five tools and the same constraints, note in the README that BeeAI was evaluated, and move on. The demo never waits on a framework.

3. Granite 4.2 3B, the voice and the report

must work
  • Speaks as the caller during the dispatch call, constrained to the Call Brief.
  • Writes the post incident report that appears on screen at the end of the run.
  • Optionally punctuates the Granite Speech output, since TurboCTC emits no punctuation, capitalisation or timestamps.

4. Granite Speech 5.0 470M TurboCTC, dispatcher questions in

fallback ready

Apache 2.0, tiny, fast. Pair with Kokoro-82M for output at 40 ms to first audio.

Hard ruleTwilio Media Streams only, raw audio. Never <Say> and never <Gather input="speech">, because both are cloud inference and they contradict the entire premise of the project.

5. AI Factsheets, the governance artefact

deliverable

A FACTSHEET.md in watsonx.governance format: every model, its role, how it was evaluated, how confidence is calibrated, known failure modes, and an explicit statement of what the system is not permitted to do. This is the single cheapest way to win the Responsible AI criterion, and almost nobody else will have one.

06

The four pillars, answered

The challenge theme is Responsible AI for Business and Society, and the four pillars are named in the brief. Each one needs a concrete artefact in the repo, not a claim on a slide.

PillarWhat we actually ship
EthicalGuardian blocks ungrounded claims before dispatch. The system never dials a real emergency number. Human review is triggered below the confidence threshold instead of acting anyway.
TransparentAppend only governance panel showing every decision and its reason. Calibrated confidence from logprobs, with the method named on screen. FACTSHEET.md. OpenTelemetry traces.
InclusiveRuns on one consumer GPU, so a community college with no surveillance budget gets the same capability as a funded campus. No per camera cloud subscription, no vendor contract. This is a real argument, lead with it.
SustainableThe router screens every frame at near zero cost and the expensive model wakes only on a hit, so compute scales with incidents rather than with camera count. Put the frames screened counter and the VLM invocation count on screen side by side.
Privacy is the fifth argument and the strongest one. Video never leaves the building. Only the alert does. The smoke detector analogy carries it: the detector is local, the fire department is not, and you cannot summon an ambulance from a local network.

Lanes and gates

Six lanes. Lanes 2, 4, 5 and 6 have zero dependencies and start at minute zero against the mock emitter. Lane 1 blocks lane 3 only.

Lane 1 · Serving

blocks lane 3 · 90 min cap
  • Stand up every endpoint in the section 02 table with explicit memory fractions. Serve, do not integrate.
  • Prove all of them coexist on 16 GB with no OOM. This is the whole night's risk, so settle it before anything depends on it.
  • Post VRAM, latency and tokens per second into context.md as you measure them.
Gate · 90 minutesAll endpoints up, or the fallbacks taken and written down. Say loudly within the first hour if something will not serve, rather than fighting it quietly.

Lane 2 · Perception, bands A to C

independent
  • MediaMTX with twelve looping feeds, decode, per camera 10 second ring buffer.
  • YOLO26s-pose plus ByteTrack. VadCLIP for the UCF-Crime classes.
  • Temporal pose rule for falls, evaluated as a sequence across frames. VadCLIP has no fall class, which is exactly why this rule exists.
  • Emit frame_screened and router_hit events only. Nothing downstream.

Lane 3 · Adjudicator, Guardian, call loop

waits on lane 1 only
  • Two completions on one cached prefill. Logprob plus temperature scaling for confidence.
  • Call Brief builder reading from camera_map.json. Deterministic, no model involved in the decision to act.
  • Guardian function call gate, then Guardian groundedness on each utterance.
  • Plant the deliberate failure case before polishing anything. It must block identically on every run.
  • BeeAI call loop with the five tools, constraints on, OpenTelemetry on.
Gate · midnightGuardian visibly blocks something, and one incident travels end to end to the dashboard with nobody touching anything.

Lane 4 · Frontend

independent · start now
  • Six camera panes with overlays, twelve pin campus map, frames screened counter, incident detail.
  • Governance panel, append only. Each row: what was seen, what was concluded, confidence, Guardian verdict, reason, timestamp. Pass green, block red.
  • Tool calls appearing live during the call, one line each.
  • The split screen Guardian shot. Passed claim beside blocked claim. Build it as a first class view, not an afterthought.
  • Build entirely against the mock emitter. Do not wait for a single backend endpoint.

Lane 5 · Scenario runner and the hardcode layer

independent
  • scenario.json: which clip, which camera, which second, for every beat.
  • Pre warm every model before the run so the first inference is not the slow one.
  • Cached verdict fallback on the hero clip. Live by default, cache only if live is slow.
  • One key reset to a known state. The run must be repeatable ten times without a restart.
  • Mock dispatch console with the scripted questions.
Gate · the real finish lineThe scenario file drives the entire run start to finish, hands off. The moment this is true, record a backup take immediately.

Lane 6 · Deliverables

independent
  • Clips: three cameras on one collapse, quiet footage elsewhere. Stock CCTV for the quiet panes, free for commercial use and safest for a public video.
  • camera_map.json with real addresses, entrances and cross streets. The Call Brief reads from this, so it has to be complete and correct.
  • FACTSHEET.md in the watsonx.governance format.
  • README.md: setup from a clean clone, how local inference works, how Guardian is wired, and the paragraph saying what is simulated.
  • Deck: problem, architecture, the Guardian shot, the four pillars, impact, the measured numbers.
  • Devpost fields drafted early, not at the deadline.

12

Hard rules

  • Never dial a real emergency number, including during testing. Dispatch is always simulated and always labelled.
  • Never commit model weights, video files, clips, API keys, passwords, credentials, or any sensitive or personal data. Check .gitignore before the first commit, not after.
  • Never use Twilio <Say> or <Gather input="speech">. Media Streams only.
  • Never send video to a cloud service. It contradicts the premise and a judge will catch it.
  • Never use DukeMTMC or any dataset withdrawn over consent concerns. Public, permissively licensed clips only.
  • Never call the adjudicator a VLA. It is a VLM. VLA means Vision Language Action and means something else entirely.
  • Never write a confidence score the model made up. Logprobs or nothing.
  • Never let Guardian only pass. If the block is not reproducible on demand, the demo has no story.
  • Never break the end to end run. Revert first, debug second.
